# План E2E-тестирования (Playwright)

## Объект тестирования

Файлообменник: Next.js-фронтенд (`http://localhost:3000`) + FastAPI-бэкенд (`http://localhost:8000`) + Celery-воркер (асинхронная обработка файлов) + Postgres + Redis. Запуск окружения — `docker compose -f docker-compose.dev.yml up` + `alembic upgrade head`.

Ключевая специфика, влияющая на тесты:

- **Асинхронная обработка.** После загрузки файл получает статус `uploaded`, воркер переводит его в `processing → processed/failed`. UI не обновляется сам — в тестах нужен polling через кнопку «Обновить» (или перезагрузку страницы) с `expect.poll` / `toPass`.
- **Общая БД между тестами.** Изоляция через уникальные title (префикс + `testInfo`), очистка через `DELETE /files/{id}` в teardown.
- **Логика скана** (порождает проверяемые сценарии):
  - подозрительные расширения: `.exe`, `.bat`, `.cmd`, `.sh`, `.js` → `suspicious` + warning-алерт;
  - размер > 10 МБ → `suspicious`;
  - `.pdf` с MIME не `application/pdf` → `suspicious`;
  - чистый файл → `clean` + info-алерт «File processed successfully»;
  - ошибка обработки → `failed` + critical-алерт.
- **Ошибки API:** 400 (пустой файл), 413 (> 100 МБ), 404 (нет файла), пагинация `limit ∈ [1..1000]`, `offset ≥ 0`.

## Фаза 0 — Инфраструктура

1. Создать `e2e/` в корне (отдельный пакет, чтобы не мешать фронтовым зависимостям): `@playwright/test`, `playwright.config.ts`.
2. Конфиг: `baseURL: http://localhost:3000`, `trace: on-first-retry`, `screenshot: only-on-failure`; проект `chromium` (при желании расширить до firefox/webkit).
3. Проверка готовности стека перед прогоном (globalSetup): дождаться `GET :8000/files` → 200 и главной страницы фронта.
4. Фикстуры тестовых файлов (генерируются на лету, не хранятся в git): `clean.txt`, `document.pdf` (с маркерами `/Type /Page`), `malware.exe`, `script.js`, `empty.txt`, `big-11mb.bin`.
5. API-хелпер на `request`-контексте Playwright: загрузка файла напрямую в бэк (для seed), ожидание статуса `processed`, удаление файлов после теста, выборка алертов по `file_id`.
6. Кастомная фикстура `uploadedFile`: загружает файл через API, регистрирует авто-очистку.

**Выход фазы:** `npx playwright test` запускается, пустой smoke-тест зелёный.

## Фаза 1 — Smoke UI

- Страница открывается: заголовок «Управление файлами», секции «Файлы» и «Алерты», кнопки «Обновить» и «Добавить файл».
- Таблицы рендерятся; при пустой выборке — «Файлы пока не загружены» / «Алертов пока нет» (проверять на чистой БД либо опустить empty-state).
- Счётчики-бейджи у секций соответствуют числу строк.
- Спиннер во время загрузки исчезает.

## Фаза 2 — Загрузка файла (happy path)

- Модалка: открытие по «Добавить файл», закрытие по «Отмена» и крестику, сброс/сохранение полей.
- Валидация: сабмит без title и/или файла → «Укажите название и выберите файл», модалка не закрывается.
- Загрузка `clean.txt` (через `setInputFiles`): модалка закрывается, файл появляется в таблице — title, имя файла, MIME `text/plain`, корректно отформатированный размер, дата.
- Статусная цепочка: сразу после загрузки бейдж `uploaded`; после polling'а «Обновить» — `processed` (зелёный), скан `clean`, детали «no threats found».
- В таблице алертов появился info-алерт «File processed successfully» с `file_id` загруженного файла.

## Фаза 3 — Сценарии скана (подозрительные файлы)

Для каждого случая: загрузить → дождаться `processed` → проверить бейджи и алерт.

- `malware.exe` → скан `suspicious` (warning-бейдж), детали содержат «suspicious extension .exe», warning-алерт «File requires attention…».
- `script.js` → аналогично для `.js`.
- `big-11mb.bin` (11 МБ) → «file is larger than 10 MB».
- `.pdf`, отправленный с MIME `text/plain` (только через API-хелпер — браузер сам ставит MIME) → «pdf extension does not match mime type».
- Комбинация (`.exe` > 10 МБ) → обе причины в `scan_details`.

## Фаза 4 — Негативные сценарии UI

- Пустой файл (`empty.txt`, 0 байт) → бэк вернёт 400 → в UI ошибка «Не удалось загрузить файл», модалка открыта, кнопка снова активна.
- Недоступный бэкенд (route abort `**/files` через `page.route`) → «Не удалось загрузить данные» при загрузке страницы; ошибка при сабмите формы.
- Кнопка «Сохранить» задизейблена и показывает «Загрузка...» во время сабмита (route с задержкой).
- (Опционально, помечен `slow`) файл > 100 МБ → 413 → ошибка в UI.

## Фаза 5 — Скачивание

- UI: клик «Скачать» → событие `download`, имя файла = `original_name`, содержимое совпадает с загруженным байт-в-байт.
- API: `GET /files/{id}/download` → 200, корректные `Content-Type`/`Content-Disposition`; несуществующий id → 404.

## Фаза 6 — API-уровень (request-контекст Playwright)

Контрактные проверки, которые неудобно гонять через UI:

- `GET /files?limit&offset`: границы `limit=1`, `limit=1000`, `limit=0` → 422, `offset=-1` → 422; корректность среза при seed'е нескольких файлов.
- `GET /files/{id}` → 200 / несуществующий → 404.
- `PATCH /files/{id}` (title) → 200, изменение видно в UI после «Обновить».
- `DELETE /files/{id}` → 204, повторный GET → 404, файл исчез из списка.
- `GET /alerts` с пагинацией.

## Фаза 7 — Стабильность и CI

- Прогон всех тестов 3× подряд (`--repeat-each`) — ловля flaky из-за асинхронной обработки; тюнинг таймаутов polling'а.
- Решение по параллельности: либо `fullyParallel` с изоляцией по уникальным title, либо `workers: 1` для сценариев, зависящих от счётчиков/empty-state.
- GitHub Actions: поднять `docker-compose.dev.yml`, применить миграции, дождаться healthcheck, прогнать тесты, выложить HTML-репорт и трейсы артефактами.

## Статус

Все фазы реализованы, тесты лежат в [`e2e/`](../e2e) (см. [`e2e/README.md`](../e2e/README.md)).

По фазе 7:

- прогоны `--repeat-each=5` (280 тестов, 16 воркеров) ×4 и `--repeat-each=3`
  под `CI=1` (2 воркера) — без flaky; два найденных источника нестабильности
  (клик до гидратации React и сверка среза пагинации с seed-файлами в общей БД)
  исправлены в коде тестов, а не ретраями — детали в `e2e/README.md`;
- параллельность: `fullyParallel: true` без serial-проектов — тесты не зависят
  от глобального состояния БД (empty-state и счётчики снимаются с моков
  роутов, пагинация — с собственного seed'а и retry-блока);
- таймауты ожидания воркера и готовности стека в CI увеличены (60 с и 180 с
  против локальных 30 с и 60 с);
- CI: [`.github/workflows/e2e.yml`](../.github/workflows/e2e.yml) — стек из
  `docker-compose.dev.yml`, миграции с ретраями, ожидание бэка и фронта,
  прогон Playwright, HTML-репорт артефактом всегда, трейсы и `docker compose
  logs` — при падении.
